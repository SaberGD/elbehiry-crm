# تقليل القراءات من قاعدة البيانات (Firestore)

Firestore بيحاسب على كل مستند بيتقري. قبل التعديل ده كان كل فتح للموقع بيقرا كل المجموعات اللي في نطاق الشخص كاملة، ومنها سجل العميل (`timelineEvents`) وسجل العمليات (`activityLogs`)، وهما أكبر مجموعتين وبيكبروا مع كل حركة.

## اللي اتعمل

| التحسين | فين | الأثر |
|---|---|---|
| تخزين محلي دائم (IndexedDB) مشترك بين التابات | `src/lib/firebase.ts` | فتح الموقع تاني خلال ~30 دقيقة بيقرا اللي اتغير بس، مش كل حاجة. الشاشات بتظهر فورًا من الجهاز. التابات المفتوحة بتشارك اتصال واحد بدل ما كل تاب يقرا لوحده. |
| سجل العميل بيتقري لما ملفه يتفتح بس | `CRMContext` (`watchCustomerHistory`)، `LeadDetailsModal`، `CustomerBrief` | بدل قراية سجل كل العملاء مع كل فتح، بيتقري سجل العميل المفتوح بس (عشرات المستندات بدل آلاف). |
| سجل العمليات بيتقري لما صفحته تتفتح بس، الأحدث أولًا 300 سجل في المرة | `CRMContext` (`requestAuditLogs`)، `AuditLogPage` | الإدارة العليا ماكانتش بتفتح الصفحة دي غالبًا ومع ذلك كانت بتقراها كلها. زر «عرض سجلات أقدم» بيجيب 300 كمان. |
| التنبيهات: آخر 200 بس | `CRMContext` | التنبيهات القديمة اتعاملت خلاص، مش لازم تتقري كل مرة. |
| نقل العميل لموظف تاني بيحدّث سجله على السيرفر مباشرة | `reassignLead` | لإن السجل مش كله محمّل، التحديث بقى استعلام + تعديل الحقلين `leadOwnerId` و`branchId` بس (نفس اللي القواعد بتسمح بيه). |
| شيلنا قراءة `test/connection` مع كل فتح | `src/lib/firebase.ts` | كانت قراءة مرفوضة من القواعد ومالهاش لازمة. |
| مسح البيانات المحلية عند تسجيل الخروج | `AuthContext.logout` | الجهاز المشترك مايفضلش عليه بيانات الشخص اللي خرج. |

البحث والفلاتر وكشف رقم الهاتف المكرر كلها بتشتغل على البيانات المحمّلة في المتصفح، فمش بتعمل قراءات ومحتاجتش indexes.

## الـ Indexes

الملف: `firestore.indexes.json` (وفيه `firebase.json` بيشاور عليه).

- `notifications`: `targetUserId` + `createdAt` تنازلي: لاستعلام «آخر 200 تنبيه ليا» للموظفين.
- `timelineEvents`: `leadId` + `branchId` + `leadOwnerId`، و`leadId` + `branchId` + `authorId`: لاستعلام سجل عميل واحد في نطاق الموظف.
- استثناء الحقول النصية الطويلة من الفهرسة (`details`، `notes`، `message`، `response`، `ai`، `text`، `items`): مافيش استعلام بيستخدمها، فإلغاء فهرستها بيقلل حجم التخزين ويسرّع الكتابة.

### النشر (مرة واحدة)

```bash
npx firebase-tools login
npx firebase-tools deploy --only firestore:indexes --project albehairy-group
```

أو من Firebase Console ← Firestore ← Indexes.

بيئتا dev وmain بيستخدموا نفس مشروع Firebase. إضافة الـ indexes مش بتأثر على كود الإنتاج، فالنشر آمن. لحد ما الـ index يتبني، التطبيق بيرجع تلقائيًا للاستعلام من غير حد (ومن غير ما يكسر حاجة) وبيكتب تحذير في الـ console. **ماتنشرش `firestore.rules` من الفرع ده**؛ الأمر فوق بينشر الـ indexes بس.

## الاختبار

`rules-tests/app-e2e.mjs` فيه فحوصات جديدة: فتح ملف عميل بيجيب سجله، نقل العميل بيحدّث سجله كله على السيرفر، صفحة سجل العمليات بتحمّل لما تتفتح، وتسجيل الخروج بيرجع لشاشة الدخول.

## أفكار للمرحلة الجاية (محتاجة قرار)

1. **مزامنة بالتغييرات فقط (delta sync)** بحقل `updatedAt` على كل مستند: بعد الـ 30 دقيقة الفتح هيقرا اللي اتغير بس. محتاجة تعديل قواعد الأمان وطريقة للمستندات المحذوفة، ومش هتشتغل صح طول ما dev وmain على نفس قاعدة البيانات والإنتاج مش بيكتب `updatedAt`.
2. **مشروع Firebase منفصل لـ dev**، عشان تجارب الأداء والبيانات ماتلمسش الإنتاج.
3. **أرشفة/تقسيم البيانات القديمة**، زي الزيارات والمتابعات المقفولة من أكتر من سنة: تتقري عند الطلب بدل ما تتحمّل دايمًا. محتاجة تعديل التقارير اللي بتحسب «كل الفترات».
4. **أرقام مجمّعة جاهزة** (Cloud Function أو PHP) للوحة التحكم والتقارير بدل ما تتحسب من كل الصفوف على جهاز كل مدير.
